------------------

activar autenticación, compras, pagos, licencias ni descargas. Todo lo
comercial permanece deshabilitado por contrato, por reglas de estado y por

CORRECCIÓN QNT-0012C (coherencia de identificadores y contratos)
----------------------------------------------------------------
1. IDENTIDAD DE PRODUCTO (db/migrations/0001_commercial_foundation.sql)
   - products.id = uuid interno PRIMARY KEY (gen_random_uuid()).
   - products.product_id = text NOT NULL UNIQUE (identificador comercial
     estable: first-triangle-ustec-m30, first-triangle-gold-m15,
     stochextreme-ustec, tm-bandas-s3-keeper).
   - products.strategy_id = text NOT NULL UNIQUE (estrategia pública).
   - ELIMINADO product_key (la ambigüedad product_id uuid + product_key text
     desaparece). Seed inserta product_id/strategy_id/display_name/status/
     delivery_format/commercial_download_enabled, idempotente ON CONFLICT
     (product_id).
   - FKs internas renombradas a product_ref uuid NOT NULL REFERENCES
     products(id) en plans, orders, licenses y entitlements; índices
     actualizados. product_id NUNCA es FK.
   - Documentado en docs/COMMERCIAL_ARCHITECTURE.md (contrato id /
     product_id / strategy_id).
2. NULABILIDAD DE CUSTOMER (src/domain/commercial/customer.ts)
   - email: string | null y displayName: string | null (coherentes con SQL
     nullable). QNT-0013 decidirá qué campos son obligatorios tras elegir el
     mecanismo de identidad. Sin usuarios creados.
3. COMBINACIONES DE FACTURACIÓN (src/domain/commercial/plan.ts + rules.ts +
   migración)
   - isBillingCombinationValid(plan): rental -> monthly|quarterly|annual;
     purchase -> one_time. Prohibido rental+one_time, purchase+monthly/
     quarterly/annual.
   - canSelectPlan exige ahora: active + combinación válida + precio real.
   - Migración: CONSTRAINT plans_billing_combination CHECK en la tabla plans.
